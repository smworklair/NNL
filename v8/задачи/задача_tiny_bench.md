# Задача: `tiny` как бенч-станция в стиле Lego (команда `tiny bench` + новый дизайн CLI)

Скопируй файл целиком в другую модель. Работа в `C:\BETA\tiny` (пакет `tiny`, CLI «штаб агентов», ~4,4 тыс. строк, Windows, Python 3.14, экран на Textual в `tui/`).

**Свобода:** код можно менять, переименовывать и переписывать, структуру пересобирать, фантазировать и добавлять идеи, если они служат цели. Ограничения только в разделе «Правила» внизу.

## Зачем
Проект NNL (Neural Network Lego) сравнивается с обычными моделями на шести тестах. Раньше «обычные модели» гоняли руками через чаты: у сайтов свои системные промты, не контролируются температура и версия. Нужна станция, которая гоняет те же промты через API в одинаковых условиях (без инструментов и поиска, фиксированная температура, независимые запросы, N повторов) и показывает результаты наглядно. Сам `tiny` — уже готовый CLI-штаб с подключением разных API, его и превращаем в эту станцию.

## Что уже есть в `tiny` (прочитай до начала)
- `backends/base.py`: `Backend.complete(system, question, history=None, temperature=0.3) -> str`, повторы при 429/503, `LLMError`, признак «квота кончилась».
- Бэкенды: Anthropic, Gemini, Mistral, GigaChat, Yandex, `openai_compat` (Groq, Alibaba и любые совместимые).
- `catalog.py` (каталог подключений с ключами), `models.py` (`make_backend`, `provider`, `describe`), `envfile.py` (ключи из `.env`).
- `hq.py` (штаб: параллельные миссии), `cli.py` (команды), `tui/` (экран с четырьмя режимами: Штаб, Файлы, Поиск, Настройка), `tui/palette.py` (тёмная палитра).

## Часть A. Команда `tiny bench`
```
tiny bench --модели A,B,C --тесты 1,2,3,4,5,6 --прогонов 3 [--температура 0.2] [--метка X] [--список] [--диалогами]
```
- `--список` — доступные подключения и модели (есть ключ).
- Промты: `C:\ЯДРО-ОПЫТ\NNL\диалог\бенч_шесть\промты.json` (`--промты` переопределяет). Формат: `{"1": {"название","текст","случаи":[…]}, …, "5": {"текст","диалоги":[[реплики]…]}, "6": {"текст"}}`.
- Тесты 1–4, 6: один запрос, `system=""`, `question` = текст промта как есть, история пустая. Тест 5: один запрос с полным текстом; с `--диалогами` — ещё и 8 диалогов по репликам с историей. Для теста 6 лимит вывода ≥ 12000 токенов, таймаут ≥ 600 с, размышление включить, если бэкенд умеет.
- По одной модели прогоны идут последовательно (лимиты в минуту), разные модели параллельно. Одна упавшая модель не роняет остальные; ошибку записывать, не прятать.
- Выход: `C:\ЯДРО-ОПЫТ\NNL\диалог\бенч_шесть\результаты\<метка>\модель-<имя>_тест<N>_прогон<k>.json` (формат совпадает с нашим `прогон_шести.py`, чтобы NNL и модели лежали рядом):
```json
{"режим": "модель:<имя>", "тест": "3", "прогон": 1, "ответ": "...сырой текст...",
 "строки": {"1": "...", "2": "..."}, "мс": 2000, "токены": 1118, "вызовов": 1, "ошибка": null}
```
  `строки` — разбор по номерам (`N. …`, в тесте 5 — `Диалог N: …`), без домыслов. `токены` — `null`, если провайдер не вернул usage (оценок «на глаз» нет). Рядом `условия.json`.
- Токены: добавь в `Backend` необязательный `last_usage` (`{"вход","выход"}`), бэкенды заполняют, если провайдер отдал usage.
- Идеи по желанию: матрица «модель × тест» с долей строк без ошибок, перезапуск только упавших ячеек, экспорт в CSV и Markdown, ожидание при лимите минуты вместо падения.

## Часть B. Новый дизайн в духе Lego
Стиль Lego — не украшение, а смысл: **независимые детали, которые сцепляются; вставил или вынул деталь — остальные не меняются**. Это и есть идея NNL (блоки на общей плате).

**Сначала концепт, потом код.** Обязательный порядок (так хочет заказчик):
1. Напиши короткий концепт (до одной страницы): метафора → что чему соответствует → список экранов. Предложи 2–3 варианта и выбери лучший с обоснованием. Остановись и покажи заказчику; код пиши после его «да».
2. После согласия — реализация в `tui/` (Textual).

**Затравка для концепта** (можно отвергнуть и придумать лучше): плата с «шипами» — это станция; каждая модель из каталога — кирпич, который защёлкивается на плату (подключить модель = вставить кирпич, отключить = вынуть, прогон остальных не затрагивается); ряд кирпичей = один тест; матрица плат «модель × тест» — главный экран с результатами; цвет кирпича — состояние (идёт, готово, ошибка, лимит), ширина или число шипов может нести реальное число (например, строк без ошибок или токенов), а не просто красоту.

**Чего не делать** (заказчик уже отвергал): кирпичики-пиксели вместо обычных столбиков «для вида»; шаблонные палитры журнальных графиков; предметную область (болезни, статьи, военкомат) в интерфейсе. Станция универсальна: тесты, модели, прогоны.

Технически: ограниченная яркая палитра (красный, синий, жёлтый, зелёный, белый, чёрный) на тёмной плате; шипы и грани средствами рамок и блочных символов Юникода; всё читается в узком терминале Windows (cmd, Windows Terminal) и без цвета деградирует до читаемого текста; клавиатура — основной способ управления; на экране видно, какие модели сейчас подключены, что идёт и сколько осталось.

## Часть C. Сессии (как в OpenCode)
Диалоги и прогоны сохраняются на диск и открываются заново. Образец поведения — окно «Sessions» в OpenCode: список по датам, строка поиска, закрепить (`ctrl+f`), удалить (`ctrl+d`), переименовать (`ctrl+r`), `esc` закрывает.
- Хранилище на диске (JSON-файл на сессию в папке данных `tiny`), а не в памяти процесса: закрытие терминала сессию не убивает. Без ключей и без чужих секретов внутри.
- Новая сессия = чистый контекст (новый чат — новая сессия). Продолжить старую можно с того места, где остановились; для диалога с NNL продолжение идёт тем же `id` сессии на сервере, если сервер не перезапускали, иначе показывается сохранённая история.
- Прогон бенчмарка тоже сессия: параметры, прогресс по ячейкам матрицы, результаты; прерванный прогон можно возобновить с недостающих ячеек.
- Название по умолчанию — первая реплика или имя прогона (не метка времени); поиск по названию и тексту.
- Режим NNL в диалоге: ход идёт на `POST http://127.0.0.1:8091/api/turn` (поля `сессия`, `режим` = `nnl|ядро|база|свободно`, `текст`, необязательно `роли`, `глубже`); трассу брать из `/api/turn_stream` (NDJSON, события `шаг`/`обновление`/`итог`) и показывать в панели трассы.

## Ключи: подтягивать сами, вручную не вводить
Все ключи лежат в одном файле `C:\KEY CLAUDE\KEY.txt` (путь можно переопределить переменной окружения `NNL_KEY_FILE`). Формат: строки идут парами, **метка в одной строке, ключ в следующей** (UTF-8, возможен BOM). Метки без учёта регистра: `api groq` (Groq), `api key` (Gemini), `QWEN` (Alibaba/DashScope), `MISTRAL`; могут быть и другие. Образец разбора: функция `_ключи()` в `C:\ЯДРО-ОПЫТ\NNL\диалог\клиент.py` и `провайдеры.json` рядом (поля `ключ_метка`, `base_url`, `модели`).
- `tiny` при старте сам читает этот файл и сопоставляет метки с подключениями каталога (таблицу «метка → провайдер» держи в конфиге, расширяемом без правки логики). Пользователь не вводит ключи руками и ничего никуда не вставляет.
- Переменные окружения (`TINY_API_KEY`, `.env`) остаются запасным путём; приоритет у файла ключей, если он есть.
- На экране и в консоли ключи не показываются вообще: для каждого провайдера только «ключ найден / не найден». В сообщениях об ошибках, логах, результатах и трассировках значение ключа заменяется на `<ключ>`. Не копируй ключи в `.env`, `условия.json` или другие файлы проекта и в историю команд.
- Файл ключей только читается: `tiny` его не меняет и не пересохраняет. Ключи не отправляются никуда, кроме API самого провайдера, которому они принадлежат.

## Правила
- Ключи: раздел «Ключи» выше. Реальные ключи из файла используются только для самого прогона через API провайдера; для остальных проверок обходись без них.
- Только стандартная библиотека (плюс уже используемый Textual), UTF-8 везде, на Windows кодировку задавать явно.
- Большой прогон по платным моделям не запускать без запроса заказчика. Для проверки — тест 3 (14 случаев), 1 прогон, одна модель.
- `промты.json` и файлы NNL не менять (читать можно).
- Баллы не считать: правильных ответов пока нет, счёт отдельным шагом.
